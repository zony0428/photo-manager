# 修正内容の確認 (Walkthrough): 重複写真スマート管理（Step 2 & Step 3: 重複スタック）

## 1. 概要
複数フォルダに同じ画像が存在する環境において、
1. **安全化 (Step 1)**: 危険な「自動付け替え（relink）」を完全停止し、オフラインドライブ切断時やバックアップ時のデータ乗っ取り事故を防止。
2. **スマート連携 (Step 2)**: 同一画像の重複検知・サムネイル高速共有（生成スキップ）・品質スコア代表選定・メタデータ自動初期連携を実装。
3. **重複スタック導入 (Step 3)**: 複数フォルダに重複する写真を **`stack_type = 'duplicate'`** として自動スタック化し、一覧画面で代表1枚にスッキリ集約表示。インスペクタやライトボックスで他フォルダのコピーをひと目で確認・比較できるようにUIを拡張。

## 2. 主な変更点と実装内容

### ① 重複写真スマート管理モジュール新設 ([`server/database/duplicates.py`](../../server/database/duplicates.py))
- **スマート品質スコア（Quality Score）算出**:
  - 解像度（画素数: 1MP=10,000点）、Exif充実度（露出値・カメラ・レンズ・GPS等: 最大75,000点）、ファイルサイズ（1MB=1,000点）、RAW原版ボーナス（+200,000点）を総合評価。
  - SNS経由や画像編集でメタデータが削られた版や縮小コピーを識別し、撮影オリジナルのマスター写真を自動特定。
- **重複写真検索 ＆ 代表写真選定**:
  - 撮影日時（`date_taken`）とファイルサイズ（`file_size`）をキーに既存DBから同一写真をミリ秒未満で高速抽出。
  - 品質スコアが最も高い写真を「代表写真（`primary_photo_id`）」として選定。
- **メタデータコピー**:
  - `copy_metadata_to_duplicate(source_id, target_id)` により、既存写真の星評価・お気に入り・手動タグを安全に連携。

### ② サムネイル生成スキップ＆高速BLOB再利用
- **個別オンデマンドサムネイル ([`server/scanner.py`](../../server/scanner.py#L540-L555))**:
  - `ensure_thumbnail` 実行時、未生成写真であっても同一画像の既存サムネイルが存在すれば、**画像デコード・LANCZOSリサイズ・WebP圧縮を完全にスキップ**し、既存のBLOBを即時再利用・保存。
- **サムネイル事前一括生成 ([`server/preload_thumbnails.py`](../../server/preload_thumbnails.py#L80-L115))**:
  - 重複写真が存在する場合、ワーカースレッドへ投入する前にメインスレッドで `save_thumbnails_batch` により一括高速複製。スキャン完了直後からサムネイルが瞬時に揃うように改善。

### ③ スキャン時のメタデータ自動初期連携 ([`server/scanner.py`](../../server/scanner.py#L595-L620))
- 新規写真のスキャン時（`smart_sync_photo` および `scan_directory`）、他フォルダに同一写真が存在すれば、既存写真の評価・お気に入りを初期値として付与し、タグを自動コピー。
- パスを書き換える「移動判定（relink）」を行わないため、元のレコードやファイルパスは100%安全に保持されます。

### ④ 重複スタック（Duplicate Stack）の自動計算 ([`server/database/stacks.py`](../../server/database/stacks.py#L370-L460))
- `recalculate_duplicate_stacks()` を新設し、フォルダスキャン後のスタック計算パイプラインの「第3パス」として統合。
- 同一画像グループの中で、品質スコア最高の原版写真を `is_stack_primary = 1`、別フォルダのコピーを `is_stack_primary = 0`、`stack_type = 'duplicate'` としてスタック化。
- 既存の連写バースト（`burst`）や露出ブラケット（`bracket`）に属する写真は最優先で保護し、破壊しません。
- 重複が解消された（削除等で単独になった）写真は自動で通常写真にリセット。
- スタックメンバー取得クエリに `directory_path` や `width`, `height` を追加。

### ⑤ フロントエンドUI対応 ([`app.js`](../../frontend/js/app.js), [`inspector.js`](../../frontend/js/inspector.js), [`lightbox.js`](../../frontend/js/lightbox.js), [`style.css`](../../frontend/css/style.css))
- **グリッドカード上のバッジ**:
  - `photo.stack_type === 'duplicate'` の場合、藍色アクセントの **「📋 重複 N」** バッジを表示。
  - スタック表示モード時、代表の原版1枚だけが表示され、同じ写真が何枚も並ぶ違和感を解消。
- **インスペクタ（右ペイン）**:
  - 重複スタック選択時、「📋 重複写真グループ (N枚)」セクションを表示。
  - 各コピーの保存先フォルダ名（`📁 フォルダ名`）、ファイルパス、解像度、ファイルサイズを一覧表示。
  - 「代表に設定」ボタンで一覧の代表写真を別フォルダのコピーに切り替え可能。
- **ライトボックス（全画面表示）**:
  - 下部のミニサムネイルピルバーに各フォルダのコピー写真を表示。
  - `←` / `→` キーやホイール、クリックで別フォルダのコピーを瞬時に比較可能。

### ⑥ 操作マニュアル & ヘルプモーダル同期
- [`MANUAL.md`](../../MANUAL.md) および [`frontend/index.html`](../../frontend/index.html) の `#helpModal` に、重複写真スタックの仕組み・キーボードショートカット説明を追記。

### ⑦ フォルダリフレッシュ・フォルダ絞り込みとの整合性強化 (Step 4 / v1.92)
- **フォルダ絞り込み時のスコープ代表フォールバック表示 ([`server/database/photos.py`](../../server/database/photos.py#L220-L245))**:
  - 重複スタックの代表写真が他フォルダにある場合、コピー写真が置かれたフォルダを開いた際に写真が0件になってしまう不整合を解消。
  - 指定フォルダ配下に実在するメンバーをそのフォルダ内での代表としてフォールバック表示するSQLクエリを導入（同一フォルダ内の重複コピーも1枚に集約）。
- **手動代表選定の優先維持 ([`server/database/stacks.py`](../../server/database/stacks.py#L450-L465))**:
  - ユーザーがインスペクタ等で同等スコアの写真同士の間で手動で代表を切り替えた後、フォルダリフレッシュや再計算が走っても、既存の代表選定がID順等で勝手にリセットされないよう優先保護ロジックを実装。
- **同一フォルダ内重複コピーの連写誤判定防止 ([`server/database/stacks.py`](../../server/database/stacks.py#L205-L215))**:
  - 同一フォルダ内に同一秒・同一ファイルサイズのコピーファイルが存在する場合に、高速連写（burst）と誤認されるのを防ぐ安全弁を追加し、第3パスの重複スタックに委ねるよう改善。
- **スタック代表切替時の全メンバー `stack_id` 同期 ([`server/database/stacks.py`](../../server/database/stacks.py#L515-L530))**:
  - `set_stack_primary` 実行時に、スタックメンバー全員の `stack_id` を新しい代表のIDに一括同期するよう修正。

## 3. 検証結果

1. **品質スコアの算出精度**:
   - `RAW版 (222,400点)` ＞ `撮影原版 (327,000点)` ＞ `縮小版 (96,236点)` ＞ `SNSメタデータ欠落版 (24,036点)`
   - 画質やExifが最も充実したオリジナル原版が確実に最高スコアを獲得することを確認。
2. **重複スタック自動作成＆代表選定**:
   - 同一写真の別フォルダ配置テストにおいて、高品質な原版が自動で `is_stack_primary = 1`、縮小コピーが `is_stack_primary = 0` となり、共通の `stack_id` が割り当てられることを確認。
   - `get_photos(stacked=True)` で代表1枚のみが返され、スタック情報に両メンバーのフォルダパスが含まれることを確認。
3. **フォルダ絞り込み・リフレッシュ整合性 (Step 4)**:
   - 全件表示で代表1枚、FolderA表示でFolderAの写真、FolderB表示でFolderBの写真が確実に表示されることを実証テストで確認。
   - 手動代表切替後に `recalculate_stacks()`（フォルダリフレッシュ）を実行しても、手動代表が維持されることを確認。
   - 高品質RAW追加時には自動でRAWが新代表に昇格することを確認。
4. **既存連写・ブラケットとの共存**:
   - 実DB内の連写バースト（5組）が重複スタックによって破壊されず、安全に保護されることを確認。
