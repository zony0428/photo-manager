# Tetheract v3 構想メモ：ローカル完結型プライベート P2P ノード連携

- **作成日**: 2026-11-10
- **位置づけ**: 将来のメジャーバージョン（`v3.0+`）に向けたアーキテクチャ構想メモ（v2 系の開発を阻害しない独立設計ノート）

---

## 1. コンセプト：クラウド／NAS 型ではなく「自律ノードのプライベート P2P」

一般的なクラウド型・セルフホスト型画像サーバー（Google フォト、Immich、Synology Photos 等）は「中央の常時稼働サーバー 1 台にすべてを集約し、PC やスマホは単なる閲覧クライアントになる」構造をとる。

これに対し、Tetheract v3 が目指すのは **「普段は各 PC・USB・スマホが 100% 単体で自律動作し、同じローカル LAN に居合わせたときだけノード同士が手を結ぶプライベート P2P（Local-First Mesh）」** である。

| 観点 | 中央サーバー／NAS 型 | Tetheract v3 プライベート P2P 型 |
| :--- | :--- | :--- |
| **データの主権** | 中央サーバー 1 台に集約（クライアントは空） | 各 PC・USB の Tetheract 自身が主権を持つ |
| **オフライン・持ち出し** | サーバー停止時や外出時は閲覧不可（または VPN 必須） | そのままノート PC や USB・スマホを持ち出して単体自走可能 |
| **バックアップ** | 常時稼働 NAS と別 HDD の管理が必要 | 同じオーナーの複数 PC / USB が LAN で出会った際に差分を預け合う（**相互バックアップ**） |
| **他者との共有** | サーバー上にゲスト用アカウントを発行してログインさせる | 友人・家族の Tetheract が同じ Wi-Fi に入った際、**公開指定したバインダーのみ**をゲスト窓口で見せ合う（離脱すれば消え、互いの DB は混ざらない） |
| **スマートフォンの役割** | 1 台の母艦のリモコン | 自分の複数 PC ノード間を行き来し、選別・フィールドログ・持ち出しバインダーを媒介するハブ |

## 2. LAN で出会ったノード間の 2 つの関係性

複雑な同時編集システムを避け、既存の `owner_id`（v1.7.0 エシカル保護）を軸に関係性を 2 種類に限定する。

1. **身内ノード連携（同一 `owner_id` 同士）＝ 相互バックアップ・差分同期**
   - 例：デスクトップ PC ⇄ ノート PC ⇄ ポータブル SSD 版 Tetheract。
   - 同一 LAN 上で互いを認識した際、新しく取り込まれた写真（`Loome` 実体またはカタログ）および評価・タグ・非破壊調整・GPS の更新差分を双方向に同期・バックアップし合う。
2. **ゲストノード連携（異なる `owner_id` 同士）＝ ショーケース公開・お裾分け**
   - 例：撮影会や家庭内で、別オーナーの Tetheract と同じ Wi-Fi に入った場合。
   - 全ライブラリは非公開のまま、「ゲスト公開 ON」に設定した特定バインダー／フォルダのみを読み取り専用ストリームとして公開する。
   - ゲスト側は手元の Tetheract の検索 UI（タグ・機材・露出・地図等）で公開範囲を閲覧でき、許可されていれば選択写真を自身の `Loome` へコピー受領できる（公開元のデータや評価は一切変更不可）。

## 3. v3 に向けた DB・キー設計の 3 原則（v2 からの進化経路）

現在の SQLite 高速構造を捨てて全面スクラップ＆ビルドする必要はなく、以下の 3 点を段階的に整備することで移行できる。

### 3.1 「内向きの主キー」と「外向きの識別キー」の二層分離
- **内向き（ローカル DB 内）**: `photos.id (INTEGER PRIMARY KEY)` はそのまま維持する。`thumbnails` の ROWID 直引きや `photo_tags (WITHOUT ROWID)` の結合速度を守るため、ローカル主キーを文字列 UUID 化してはならない。
- **外向き（ノード間通信・スマホ同期）**: ローカル連番 `photo_id` を通信ペイロードの主識別子として使わず、必ず **`content_key`（写真固有ハッシュ＋EXIF識別子）** と **`tag_key`（タグ不変ID）** のみで照合する。

### 3.2 `owner_id` ＋ `library_id`（`node_id`）の 2 階層アイデンティティ
- **`owner_id`**: 持ち主（同一人物か他者＝ゲストか）を表す識別子。
- **`library_id` / `node_id`**: 同一オーナー配下の個々のライブラリ個体（メイン PC、サブ PC、USB、開発環境など）を区別する不変 UUID（`app_meta.library_id` として v2.1.0 の混線防止ガードから先行導入）。
- **所在リンクの拡張**: 既存の `photo_links`（`volume_serial` + `rel_path`）を拡張し、「どの `node_id` が元ファイル実体を保持しているか」を記録できるようにする。

### 3.3 「DB 丸ごと上書き」から「項目別変更ジャーナル（LWW）交換」へ
- 現状の `photos.updated_at` 単一列では、PC-A で付けた「タグ」と PC-B（またはスマホ）で付けた「評価」の競合を正しくマージできない。
- Android ロッカーで導入した `PendingJournalStore`（`rev` 管理）を発展させ、PC 本体側にも **項目単位の更新ログ（`node_id`, `hlc_timestamp`, `content_key`, `field_type`［rating / favorite / tag_add / tag_remove / tone / crop / gps］, `value`）** を持たせ、ノード間で未取得の `rev` 以降のログを交換して収束させる（Last-Write-Wins Element Set）。
