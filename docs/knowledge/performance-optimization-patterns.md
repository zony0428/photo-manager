# パフォーマンス最適化パターンと委譲開発の教訓（v1.36）

2026-10 のパフォーマンス監査（v1.35→1.36）で確立した実装パターン、計測手法、落とし穴をまとめる。
詳細な経緯は `docs/performance_audit/`（implementation_plan / delegation_prompts / walkthrough）を参照。

## 1. 確立した実装パターン

### 1.1 フォルダ絞り込みは `_directory_filter_sql()` を必ず使う
`server/database/photos.py` の共通ヘルパー。LIKE は以下の理由で**使用禁止**。

| LIKE の問題 | 範囲比較での解決 |
|---|---|
| `_` がワイルドカードになり、`Photo_1` で `PhotoX1` が一致してしまう | 文字コードの範囲比較なのでワイルドカードが存在しない |
| 大文字小文字を区別しない比較ではインデックスが効きにくい | `COLLATE NOCASE` と `idx_photos_directory_nocase` で範囲 SEARCH になる |

- 配下の判定には「`'\\'` の次の文字は `']'`、`'/'` の次の文字は `'0'`」を利用する。
  - 例: `col >= 'C:\a\' AND col < 'C:\a]'`
- **下限は `>=`** にする。`>` だと `C:\` のような末尾区切り付きのドライブ直下が漏れる（実際に発生した退行）。
- 非再帰の場合も `norm + '\\'` を一致候補に含める。

### 1.2 大きな JSON 応答は `_fast_json()` を使う
FastAPI 標準の `jsonable_encoder` は 5,000 件で約440ms かかる。`json.dumps(..., ensure_ascii=False, separators=(",",":"), default=str)` を `Response` で直接返すと、約50ms で済む。orjson は採用していない（標準ライブラリで十分）。

### 1.3 差分スキャン（size + mtime）
- `photos.file_mtime REAL` に `stat().st_mtime` を保存する。
- 再スキャン時は `get_existing_photos_map()` で既存レコードを1回のクエリで先読みする。
  - `file_size` と `file_mtime` の両方が一致（mtime の差が 1e-4 未満）したファイルは、メタデータ解析を省略して `unchanged` とする。
  - mtime が NULL の行（旧データ）は通常どおり解析し、mtime を埋める。
- 変更を検出したファイルはサムネイルを削除して再生成させる。
- DB への反映は `upsert_photos_batch()` で 200 件ずつ行う。

### 1.4 スタック再計算は「差分 UPDATE」
現在値を `current_vals` に保持し、値が変わる行だけを `executemany` でまとめて更新する。
**注意**: 旧実装は SELECT に `paired_raw_path` を含めていなかったため、ステップ1で明示的に設定されない写真の値は None として扱われていた。SELECT に列を追加するときは、旧実装と同じ意味になるよう明示的に `pop` すること（実際にずれが発生した）。

### 1.5 サムネイル生成
- `render_thumbnail_webp()` に処理を統一した（クラウドファイル、RAW、通常画像）。
- JPEG では `draft("RGB", (max*2, max*2))` と `thumbnail(..., reducing_gap=2.0)` を使う。1枚あたり 92ms から 39ms になった。
- 一括生成は `ThreadPoolExecutor(4)` で並列化し、DB保存は呼び出し元スレッドでバッチ実行する。多重起動はモジュールレベルのロックで防ぐ。
- **future は集合で管理し、処理済みのものから `discard` する**。リストのまま保持すると、生成済みの WebP を全件分メモリに抱え込む。

### 1.6 フロントエンド
- **選択表示の差分更新**: `lastSelectedPhotoIds` との差分だけ classList を更新する（差分が50件を超えたら全走査）。グリッドを再描画するときは、差分の基準を**現在の選択集合に同期する**（clear にすると、再描画後に選択を外してもハイライトが残る）。
- **評価変更**: グリッドの全再描画をしない。フィルタ外になった写真だけを `removePhotoFromView()` で除去する。
  - あわせて選択、Shift範囲選択の起点、ライトボックスの index を補正する。
  - 段階描画（rAF チャンク）の途中では index がずれるため、全再描画に切り替える。
- タグや評価の一括操作のあとは `refreshAll()` を使わず、必要なもの（`fetchPhotos` / `fetchTags`）だけを再取得する。

### 1.7 TTL キャッシュはクリア処理の配線までが1セット
`clear_online_cache()`（scanner）と `clear_folders_fs_cache()`（folders）は、`scan_directory` の開始時に呼ぶ。キャッシュを追加したら、無効化をどこで行うかを必ず決める。

**否定キャッシュで省くのは「遅い処理」だけにする（v1.37 で修正）**: `resolve_portable_path()` は当初、親フォルダがオフラインと記録されると即 `False` を返していた。そのためドライブレター変更時に、同じ親を持つ別フォルダ（別ドライブ側には実在）までオフライン扱いになった。省くのは切断ドライブでブロックし得る元パスの `exists()` だけにし、ローカルの代替照合は常に行う。キャッシュは「元パスの親が実在するか」だけを表し、代替照合の成否では書き換えない。

## 2. 計測と回帰検証の手法

- **ベンチマーク**: `scratch/perf/bench.py --fresh`
  - 本番DBを sqlite の backup API で `.cache/bench_copy.db` に複製し、`server.database.connection.DB_PATH` を差し替えてから計測する。
  - 本番DBには一切書き込まない。
- **旧版との全件比較**: `git show HEAD:path` で旧モジュールを `types.ModuleType` に読み込む（`__package__ = "server.database"` を設定すると相対 import が通る）。旧版と新版で同じ処理を別々の複製DBに実行し、結果列を全件比較する。
  - スタック再計算: 12,596 件で差分 0。
  - フォルダ絞り込み: 92 フォルダで件数一致。
- **差分スキャン**: 実在する小さなフォルダを複製DBで2回スキャンし、2回目がすべて `unchanged` になることを確認する。

## 3. 安価な Agent への委譲で得た教訓

1. **自己報告は信用しない。統合時に差分の実物をレビューする。** 今回、全 WP が「完了」と報告したが、統合レビューで不具合 6 件と未配線 1 件が見つかった。
2. **委譲プロンプトに UX の仕様を書くときは、旧版の実際の挙動をコードで確認してから書く。** 当初の理解が曖昧なまま「フィルタ外の写真は消える」と指示した。実際にはマニュアルが「棄は自動で隠れる」と記述していたが、旧コードは消していなかった（文書と実装の乖離）。最終的に、ユーザーの判断で「消える」に統一した。
3. **「新しい関数を用意したが、呼び出しはしていない」状態が起きやすい。** 受入基準に「どこから呼ばれるか」を含める。
4. **改行コードと文字化け**: Agent によって LF で保存されたり、`????` の文字化けが混入したりする。統合時に機械的に検査する（CRLF の統一、`????` の grep）。
5. **検証用のファイルが散らかる**: テスト用DB（1つ約170MB）が `.cache/` に複数残っていた。委譲時に「検証用ファイルは作業後に削除」と明記する。
6. **API 応答の項目を削るときは、受け取ったオブジェクトの「渡され先」まで追う。** v1.36 で `stack_photos` から `camera_model` / `lens_model` / `iso` などを削ったところ、`sp.xxx` の直接参照は無かったが、`updateLightboxContent(sp)` に渡していたため、ライトボックスでコマを切り替えると EXIF が消える回帰が起きた（v1.35 の新機能と並行作業で衝突）。v1.37 で `ensureStackMemberDetail()` による遅延取得にした。軽量版オブジェクトを汎用の表示関数に渡す箇所を grep で洗い出すこと。
